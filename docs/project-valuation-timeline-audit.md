# Project calendar-axis audit

## Finding

Operations & Series already reads `parsedSelectedProject.engineInputWithoutPrices.yearsByPeriod`.
For current stored `project_json_v2`, `parseProjectJsonV1` creates that axis with
`resolveV2TimeAxis(masterN, productionStartPeriod, productionStartYear)`; raw
`periodEndDatesUtc` is not a V2 schema requirement. Corporate uses the same resolver.
The rejected projects therefore had an absolute parsed axis even though their raw
`time` object legitimately contained only `masterN`, `productionStartPeriod`, and
`productionStartYear`.

The first verifier incorrectly made raw `time.periodEndDatesUtc` mandatory for every
version. The previous Project chart bug was separate: on a chart-flow/FCFF length
mismatch, `computeProjectViewMetrics` used `period + valuationPeriodOffset`, producing
`-1/3` and `4/6`. The chart adapter itself only consumes timeline `calendarYear`.

## Actual sources and schemas

* **Diablillos / current template (V2):** `time={masterN, productionStartPeriod,
  productionStartYear}`; parsed years are generated by `resolveV2TimeAxis` and are what
  Operations displays. No raw dates are required.
* **Los Ricos South legacy fixture (V1):** raw `periodEndDatesUtc` contains 2025–2043,
  `masterN=18`, 19 period arrays, and production index 4/year 2029.
* **Los Ricos North legacy fixture (V1):** raw dates contain 2026–2039, `masterN=13`,
  14 period arrays, and production index 5/year 2031.
* **AbraSilver control (V2):** canonical test axis 2026–2032 with production index 3/year
  2029; it remains unchanged.
* **Empty-year project:** no repository fixture identifies the external stored project.
  The reproduced empty-axis case has neither parsed years, `yearsByPeriod`,
  `calendarYears`, nor dates and now reports precisely that no absolute period years can
  be derived. It never guesses years.

The actual external database is not checked into this repository, so raw FCFF values and
the identity of the unnamed empty-year record cannot be truthfully reconstructed here.
The checked-in real Los Ricos fixtures and current Diablillos template are exercised
period-for-period.

## `masterN` semantics

Current V2 is unambiguous: `masterN` is the inclusive final index, the resolver creates
`masterN + 1` years, the parser requires `masterN + 1` series entries, and engines loop
from 0 through `masterN`. Legacy V1 conversion explicitly accepts both `masterN` and
`masterN + 1` array lengths. Normalization therefore uses the actual normalized/FCFF
period count; verification requires V2=`masterN+1`, while V1 permits the two documented
legacy forms and still requires FCFF to equal the normalized axis.

## Normalize, then verify

`normalizeProjectCalendarAxis` uses this priority:

1. parsed canonical years (the Operations source),
2. normalized `yearsByPeriod`,
3. normalized `calendarYears`,
4. years extracted from valid `periodEndDatesUtc`.

`verifyNormalizedProjectCalendarAxis` then checks schema-specific period count, FCFF
length, production index/year, strict chronology, and—when raw dates exist—date/year
identity. V2 requires explicit production year but not raw dates. V1 dates are reconciled
when present without retroactively imposing V2 requirements.

The verified axis is passed to Project valuation timeline and chart. The discount offset
is retained solely for valuation distance, so valuation amounts do not change. Missing
or inconsistent axes suppress the chart and display `Ej verifierad` with the actual
reconciliation failure. Direct and Corporate-origin selection both load the same full
stored JSON; Corporate contributions join on the same resolved absolute years.
